# History at billion dimensions

Implementation checked: 2026-10-01.

## Memory is the constraint

The generated-text model measured here has 1,047,732,224 FP16 coordinates.

| Payload | Bytes | GiB |
| --- | ---: | ---: |
| One weight row | 2,095,464,448 | 1.952 |
| One recyclable historical row | 2,095,464,448 | 1.952 |
| 128 historical rows | 268,219,449,344 | 249.799 |
| 128-by-128 FP32 distance matrix | 65,536 | 0.000061 |

These are payloads, not total process memory. The incumbent, pending proposal,
scorer workspace, metadata, and OS need additional memory. Full resident history
cannot fit the 24 GB machine.

The small matrix can preserve known pairwise distances. It cannot determine an
arbitrary new candidate's distances without additional geometric information.

## What the search keeps

[SearchState](../rust/crates/ennx/src/bf16_metal.rs) holds one recyclable full
historical row plus a replay origin, incumbent, proposal, logical outcomes,
variances, identities, and a bounded distance matrix.
At capacity 128, history resets to the incumbent; it is not a perpetual rolling
128-point archive. The configured history geometry determines what the distance
matrix means.

### Realized geometry

`history_geometry = "realized"` is the default. It measures the FP16 models that
are actually evaluated. The implementation records the seeded proposal lineage
and replays historical rows in coordinate tiles on Metal. It rounds after each
accepted update, so the result retains sequential FP16 semantics without storing
128 full models.

This mode is exact for the replayed device program, but its work grows with both
model dimension and history. Four candidates against 128 observations require
hundreds of billions of coordinate comparisons. It is the validation oracle,
not the intended fast geometry for sustained billion-coordinate runs.

### Latent proposal-tree geometry

`history_geometry = "latent"` defines every Rademacher proposal as a new
orthogonal edge in a latent coordinate tree. If candidate `c` branches from
base `b`, its squared distance to historical observation `h` is:

```text
distance2(c, h) = distance2(b, h) + edge_norm2(c)
```

The edge norm is computed analytically from the complete block manifest:

```text
edge_norm2(c) = sum_blocks block_length * metric_weight * (block_scale * radius)^2
```

This is exact in the declared latent metric. It is not claimed to equal the
realized FP16 Euclidean distance, and it is not a low-rank projection or sampled
approximation. Candidate materialization, inference, generated tokens, reward,
and acceptance still operate on the complete realized FP16 model.

The new candidate's history geometry costs one pass over the tensor-block
manifest plus a linear scan of the small history arrays. It performs no replay
of old billion-coordinate models. Gaussian perturbations are rejected because
their realized direction norm is not determined by block length and scale alone.

The resolved `generation.json` records `history_geometry`, so a latent result
cannot be reported as realized-weight geometry.

## Why seeded replay remains available

These vectors are generated by a known program, not arbitrary externally supplied
arrays. A compact recipe can therefore describe them without changing their
full-coordinate search space:

- an exact checkpoint, or reproducible initial weights;
- every accepted update needed to reach a historical base;
- each observation's base ID, seed/stream, radius, noise law, tensor manifest
  and fixed scales, dtype/rounding, and generator implementation identity;
- stable observation identity, reward, variance, and dependency lifetime.

For a tile of coordinates, realized mode reconstructs the accepted-base lineage,
rounding to FP16 after every accepted update. Rejected observations branch from
their recorded base but do not change that lineage. It generates historical
proposal tiles and reduces distances against new candidate tiles without
retaining whole historical rows.

This bounds scratch memory by tile size and history batch size, plus one
checkpoint/current-model state. It does not make computation independent of
dimension or history. Periodic checkpoints can bound replay depth but cost
roughly 1.952 GiB per full checkpoint. Their storage tier and I/O must be measured.

Do not replace sequential rounded updates with a sum of seeded ideal directions:
FP16 rounding is not distributive. Replaying from the current incumbent by
subtracting old deltas is not generally invertible either. A seed without its
base lineage is insufficient. Same-device bitwise replay must be demonstrated;
cross-device Gaussian math and compiler changes need separate qualification.

## Options and decision

| Approach | Geometry | Cost/trade-off |
| --- | --- | --- |
| Latent orthogonal proposal tree | Exact latent geometry | Implemented; no historical tensor replay; Rademacher only |
| Seeded tiled replay | Exact realized geometry | Implemented; small history metadata; cost grows with dimension and history |
| More resident full rows | Exact to those rows | About 1.952 GiB extra per row |
| Disk-backed full rows | Exact stored values | About 249.8 GiB for 128 rows; streaming latency, not just storage |
| Projection/sketch | Approximate | Changes the metric and requires explicit research-scope approval |

The research comparison is now direct: run matched seeds and evaluation budgets
under `realized` and `latent`, then compare proposal latency, acquisition choices,
accepted rewards, and held-out generation. Latent geometry earns its place only
if removing replay preserves or improves optimization quality.

## Certified realized filtering

Realized geometry now records a shadow certificate report after full replay; it
does not prune production work yet. For each tensor family, let `A` be the
cached incumbent-to-history squared distance and `E` the candidate-to-incumbent
squared distance. The diagnostic forms the triangle bounds

```text
lower = sum_f (sqrt(A_f) - sqrt(E_f))^2
upper = sum_f (sqrt(A_f) + sqrt(E_f))^2
```

and reports how many rows would survive raw and self-tuned top-k filtering. The
selected row is still obtained from complete replay, so the report can count
both bound violations and incorrectly removed exact neighbors before any speed
claim is made. B+ANN may order work, but it cannot certify a prune.

A two-round 4,096-token smoke run reached history two and increased proposal
time from 139.453 ms to 463.899 ms under AC Low Power Mode. All rows necessarily
survived because `k = history = 2`. More importantly, each candidate had one
strict floating-point bound violation at the incumbent row, although no exact
top-k row was lost. This falsifies using raw FP32 component sums as mathematical
certificates. Production pruning remains disabled until the Metal component
kernel emits outward-safe intervals; guessed epsilons are not acceptable.

## Learned tensor-family metric

Latent edges retain one analytic component per tensor family. The existing
metric learner may reweight those components, but only after its held-out
leave-one-out likelihood exceeds the incumbent metric by the configured gate.
The index, query distances, local scales, and fitting matrix therefore continue
to use one internally consistent metric. See [metric learning](metric-learning.md).
